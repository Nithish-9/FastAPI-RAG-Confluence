Section 1.3.2 — Runtime Fault Tolerance
Add a third bullet under the existing two:

Queue Saturation (Backpressure Gate): If the workspace_embed, workspace_dbwrite, enterprise_embed, or enterprise_dbwrite Celery queues exceed a configurable threshold (QUEUE_DEPTH_THRESHOLD, default: 1000), the API rejects new ingestion requests with a 429 Too Many Requests response. The Go CLI's existing exponential backoff + jitter retry mechanism naturally backs off and retries when the system recovers. This prevents Redis memory exhaustion and cascading worker failures during large-scale indexing operations or downstream service outages.

Section 2.2.2C — The Backpressure Mechanism
Update the existing content — currently it only describes embed worker → dbwrite backpressure. Add:

API-Layer Backpressure (Upstream Gate): In addition to the embed worker's internal throttle, a second backpressure gate is implemented at the API layer. The require_workspace_ready() and require_enterprise_ready() guards — called on every /create-index and /delete-index endpoint — check queue depths via LLEN before accepting new work. If any downstream queue is saturated, the API returns 429 immediately, preventing new files from entering the pipeline entirely. This is the first line of defense; the embed worker's internal throttle is the second.
